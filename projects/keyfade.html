KeyFade: expiring secret-sharing links

KeyFade is a self-hostable application for sharing a password or other short-lived secret through a link with an expiry. It combines a browser interface with a Node.js API and Azure Key Vault storage.

  • Node.js
  • Express
  • Azure Key Vault
  • Docker

The problem it addresses

Passwords and temporary access details can remain in ordinary chat or email histories long after they are needed. KeyFade provides a workflow for creating a time-limited link that a recipient can use to retrieve a shared value.

The project is designed to be deployed by the organisation using it, with Azure Key Vault as the backing store for secret values.

How the workflow works

  1. The sender enters a secret and chooses an expiry period: 1, 7, 14, 30, 60 or 90 days.
  2. The API generates a unique identifier and a separate random access key, then stores the secret and key as separate Azure Key Vault entries with expiry dates.
  3. The sender shares the generated link with the intended recipient.
  4. The recipient can retrieve the value while the link is valid. The link holder can also delete the secret before expiry.

Implementation details

Browser interface

The EJS-rendered frontend provides create, copy-link, retrieve, copy-secret and delete states. The browser sends create, retrieve and delete requests to the API.

API and secret storage

An Express service validates requests, generates identifiers and access keys, and uses Azure Identity and the Azure Key Vault SDK to store and retrieve secret entries with expiry.

Abuse visibility

Rate limiting and structured logging support service protection and troubleshooting. Optional webhook notifications and an abuse-telemetry endpoint expose events such as failed attempts and rate-limit activity.

Deployment

The application is containerised for Docker deployment and includes Azure deployment resources and configuration guidance.

Security model

The current implementation sends the entered value to the backend API, which stores it in Azure Key Vault. The service and its Azure environment are therefore part of the trust boundary; this implementation is not client-side or zero-knowledge end-to-end encryption. Deploy it only where the service operator and Key Vault access model are trusted.

Sharing links are bearer links: anyone who obtains a valid link may be able to access the secret until it expires or is deleted. Choose the sharing channel and data carefully.

What this project demonstrates

  • Integrating a Node.js service with Azure Key Vault and Azure Identity.
  • Designing create, retrieve, expire and delete flows for temporary data.
  • Adding rate limiting, structured logging and abuse telemetry.
  • Packaging an application for self-hosted container deployment.

Source code and documentation

The repository includes frontend and backend source, container files, an Azure deployment template, API routes and configuration guidance.
